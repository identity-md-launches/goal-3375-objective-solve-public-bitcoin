# Checkpoint and resume limitations

## `-tames` saves tame precomputation, not a full checkpoint

Upstream RCKangaroo's `-tames <file>` option stores **tame-kangaroo
precomputation**: a database of distinguished points generated by tame walks for
a given range. If the file does not exist, the solver generates tames (requires
`-max`) and writes them; if it exists and matches the range, the solver loads
them to start a later solve with a head start.

What `-tames` does **not** do:

- It does **not** save the wild-kangaroo walk state of an in-progress solve.
- It does **not** record per-kangaroo positions, the live distinguished-point
  table of the current run, or collision bookkeeping.
- It is **not** a crash-resume of a real solve. Killing a real run and
  restarting it does not continue from where it stopped; it restarts the wild
  search (optionally reusing the saved tames).

Upstream states this directly in its README limitations: "No advanced features
like networking, saving/loading DPs, etc."

## Do not advertise full resume

This adapter deliberately does **not** claim resumable real-key execution. The
only durable artifact across runs is the tames precomputation, and only for a
fixed range. Treat a long real-key run as non-resumable: budget the whole run,
and if it is interrupted, expect to restart the wild search.

## Keeping this out of mandatory offline tests

The tames/checkpoint path depends on running the real GPU solver and is not
exercised by the mandatory offline CPU tests. The offline suite
(`tests/test_output_path.py`) covers only the candidate-fd output path, leak
scrubbing, fail-closed behavior, and manifest verification — none of which touch
`-tames`.
